## 3. Ответы на вопросы

### 1. Сколько секунд шёл job build в первом прогоне и сколько во втором? Какой слой Dockerfile взят из кэша и почему именно он?
* В первом холодном прогоне сборка заняла около **1m 20s**, во втором повторном прогоне около **18s**.
* Из кеша (`type=gha`) был полностью взят слой установки зависимостей: `RUN uv sync --frozen --no-dev --no-install-project`. Инструкция `COPY pyproject.toml uv.lock README.md ./`, стоящая перед этим шагом, не менялась между коммитами. Docker проверяет контрольные суммы файлов слоя: если входные манифесты зависимостей идентичны, кеш остаётся валидным и тяжёлый шаг скачивания колёс пропускается.

### 2. В логе deploy во время выката видны поды в ImagePullBackOff, а прогон при этом зелёный. Откуда эти поды и почему это не ошибка?
* При первоначальном создании Deployment кластер `kind` сразу пытается скачать образ из реестра `ghcr.io`. Так как пакеты GHCR по умолчанию приватны, первая попытка скачивания без секрета завершается ошибкой `ErrImagePull` -> `ImagePullBackOff`. Это не ошибка, потому что в этот же момент пайплайн создаёт секрет авторизации `ghcr-auth` и патчит `default serviceaccount`. Kubelet делает повторные попытки скачивания, подхватывает новые учетные данные, скачивает образ и переводит поды в `Running`. Команда `rollout status` дожидается успешного запуска, поэтому прогон остаётся зелёным.

### 3. Какой путь проходит пароль базы от страницы настроек GitHub до переменной окружения в поде? Почему его нельзя положить в configmap.yaml?
* Настройки репозитория GitHub (`Settings -> Secrets -> DB_PASSWORD`) -> раннер GitHub Actions (`${{ secrets.DB_PASSWORD }}`) -> утилита `sed` подставляет значение в манифест `k8s/secret.yaml` -> `kubectl apply` сохраняет зашифрованный объект `Secret` в `etcd` кластера -> через директиву `secretRef` в `deployment.yaml` kubelet монтирует его как переменную окружения `DATABASE_URL` внутрь контейнера. Нельзя складывать в configmap.yaml, так как манифесты ConfigMap хранятся в открытом виде в git-репозитории, видны в логах версионирования и не шифруются в etcd без специальных плагинов. Любой человек с доступом к чтению репозитория узнал бы пароль от базы.

### 4. Уберите мысленно `needs: tests` у job build. Опишите сценарий, в котором это закончится плохо.
* Без `needs: tests` джобы `tests` и `build` запускаются параллельно. Если разработчик коммитит код с критическим багом или уязвимостью, тесты упадут, но `build` проигнорирует падение, успешно соберёт сломанный образ, присвоит ему теги коммита и `latest`, и запушит в GHCR. Если продакшен или другие системы настроены на автодеплой свежих образов из реестра, сломанный сервис попадёт к пользователям, несмотря на красные тесты.

### 5. Почему на pull request у вас бегут только тесты, а build и deploy нет? Какая строка за это отвечает и зачем так сделано?
* Директива `if: github.event_name == 'push' && github.ref == 'refs/heads/main'` в описании джоб `build` и `deploy`.
* Зачем так сделано: 
  1. Безопасность: Pull Request может открыть любой контрибьютор, и автоматическая сборка с доступом к секретам реестра (`GITHUB_TOKEN` с правами на запись) создала бы угрозу безопасности.
  2. Экономия ресурсов и чистота реестра: нет смысла собирать Docker-образы и тратить минуты раннера на каждый промежуточный черновой коммит в ветке. В PR проверяется только качество кода (линтер и тесты).

### 6. Зачем в init() стоит `pg_advisory_xact_lock`? Что произойдёт без него при двух репликах и пустой базе? Реплики чего именно здесь имеются в виду?
* Имеются в виду 2 реплики пода нашего сервиса `toxic-service` (`replicas: 2` в Deployment). Без него при одновременном старте двух подов к свежей пустой базе оба пода в методе `lifespan` попытаются в параллельных транзакциях выполнить `CREATE TABLE IF NOT EXISTS prediction_logs`. В PostgreSQL параллельное создание одной и той же таблицы вызывает конфликт уникальности в системных каталогах, что приведёт к аварийному падению одной из реплик при старте.
* Блокировка `pg_advisory_xact_lock(42)` заставляет второй под подождать, пока первый под завершит транзакцию создания таблицы, гарантируя атомарность инициализации.

### 7. В трёх ваших красных прогонах поды застряли в трёх разных статусах. Расположите эти статусы в порядке жизни пода и объясните, на каком шаге возникает каждый.
Порядок по жизненному циклу пода:
1. **`Pending` (поломка 3, ресурсы):**
   * Шаг: планирование (Scheduling). Под создан в API-сервере, но планировщик `kube-scheduler` не может назначить его ни на одну ноду из-за нехватки свободной памяти. До запуска контейнера дело не доходит.
2. **`CreateContainerConfigError` (поломка 2, секрет):**
   * Шаг: инициализация окружения контейнера. Под успешно назначен на ноду, `kubelet` начинает сборку песочницы контейнера и пытается прочитать указанный в `envFrom` секрет `toxic-secret-broken`. Секрет не найден, сформировать переменные окружения невозможно, контейнер не может быть создан.
3. **`Running (0/1 Ready)` (поломка 1, конфиг):**
   * Шаг: выполнение контейнера и проверка готовности. Контейнер успешно запущен процессом ноды, но приложение внутри не прошло проверку готовности, так как упало при попытке открыть отсутствующий файл модели. Под исключается из балансировки трафика.

## 4. Журнал проблем

1. **Пустой тег образа в Docker Buildx (`invalid tag ":sha"`):**
   * Ошибка: `buildx failed with: ERROR: failed to build: invalid tag ":fcd09...": invalid reference format`.
   * Попытка вычислить имя образа через bash-команду с записью в `$GITHUB_ENV` приводила к потере переменной из-за переносов строк Windows. Переменная `IMAGE_NAME: ghcr.io/${{ github.repository }}` вынесена напрямую в блок `env:` джобы GitHub Actions.

2. **Ошибка применения манифестов Kubernetes (`no objects passed to apply`):**
   * Ошибка: `error: no objects passed to apply` на шаге применения `k8s/secret.yaml`. 
   * Файл `k8s/secret.yaml` был случайно закоммичен с размером 0 байт, а локальные изменения с содержимым секрета не были запушены в remote-репозиторий. Файл заполнен корректным манифестом `Secret` и отправлен в `main`.

3. **Несовпадение ответа `/health` в юнит-тестах:**
   * Ошибка: `AssertionError: assert {'status': 'ok', 'model_path': ...} == {'status': 'ok'}`.
   * Эндпоинт `/health` был модифицирован для отображения настройки из ConfigMap, а старый тест ожидал только ключ `status`. Тест `test_health_check` обновлён для проверки наличия `model_path` в словаре ответа.
